# AGENTS.md — working guide for AI coding agents

dotKolam (npm: `dotkolam`): a JSON specification for rule-bound **sikku
kolam** (mirror-curve model: one bit per interior gate), with a
zero-dependency TypeScript reference implementation (validator, deterministic
generator, SVG renderer, CLI) and a formal-verification ladder (exhaustive
model checking → Z3 symbolic proofs → independent differential model). The
canvas app lives in its own project: **OpenKolam**
(https://github.com/LogicIncZo/OpenKolam), which consumes this package from
npm. Start from `README.md` (overview, repository map) and `SPEC.md` (the
normative specification). Verification results and what is proven at what
bound: `docs/verification.md`.

## Hard invariants (breaking any of these is a bug, not a design change)

1. **Determinism.** All generation, analysis, rendering, and export paths are
   deterministic: seeded RNG only (`src/gen/rng.ts`). Never introduce
   `Math.random`, `Date.now()`, `performance.now()`, iteration-order-dependent
   logic, or float-to-output nondeterminism into `src/`. CI regenerates
   `examples/` + `motifs/` and fails on any diff — output must be
   byte-stable across runs and platforms.
2. **The permutation model is law.** The trace is a permutation on directed
   channel states: every orbit is a closed cycle, no loose ends, no retracing,
   every undirected lattice edge traversed exactly twice, every dot encircled
   (properties P1–P3 in `docs/verification.md`). Code in `src/core/` must
   preserve these; the validator (`src/core/validate.ts`) must keep checking
   them.
3. **Validator completeness & consistency (P7).** The validator is
   mutation-tested and cross-checked against `schema/kolam-1.0.schema.json`
   (ajv). Every new validation rule needs a test that a hand-mutated doc
   rejects, and must agree with the schema (schema-accepts ⇒ validator-accepts
   modulo semantic-only rules).
4. **Zero runtime dependencies.** `dependencies` stays empty. Dev deps are
   tooling only (typescript, tsx, ajv, marked, @types/node). Do not
   add a runtime dependency; implement it or justify an exception to the
   maintainer first.
5. **Strict TypeScript.** `strict`, `noUncheckedIndexedAccess`,
   `exactOptionalPropertyTypes` are on (see `tsconfig.json`). No suppression
   flags in `tsconfig.json`; use targeted non-null assertions only where the
   invariant is proven (as existing code does), never `any`.
6. **Public barrel stays browser-safe.** `src/index.ts` is the npm package's
   single export; it re-exports core/gen/prompt/render and must never pull in
   `cli.ts` or Node built-ins — OpenKolam bundles it for the browser.

## Commands

Node 22 (CI), ESM everywhere. From the repo root:

```bash
npm install                          # dev deps only
npm run build                        # tsc typecheck → dist/ (incl. the npm package entry)
npm test                             # Tier-A suite (unit + exhaustive sweeps)
npm run verify                       # npm test + Z3 proofs + differential check
npm run kolam -- <cmd>               # CLI: generate | validate | info | prompt (see README)
npm run docs                         # rebuild docs site into site/
npx tsx scripts/examples.mts         # regenerate examples/ + motifs/ (determinism baseline)
npx tsx scripts/export-loops.mts     # export differential data → formal/z3/data/ (gitignored)
```

- `npm run verify` needs `python3` + `pip install z3-solver` (CI installs it;
  locally the Z3 tier degrades gracefully if absent). `formal/z3/verify.py` is
  an **independent** Python model — keep it independent: it must never import
  from, mirror the structure of, or be generated by the TypeScript code.
- Full CI parity: `npm run build && npm run verify && npx tsx
  scripts/examples.mts && git diff --exit-code examples motifs && npm run
  docs` (see `.github/workflows/ci.yml`).

## Change protocol

Run before finishing any task:

1. `npm run build` (typecheck), then `npm test`. If you touched
   `src/core/`, `src/gen/`, or anything with formal counterparts: `npm run
   verify` (requires local z3; note in your summary if unavailable).
2. If a change legitimately alters generated output, run
   `npx tsx scripts/examples.mts` and commit the regenerated `examples/` +
   `motifs/` **in the same commit** as the code change — they are the CI
   determinism baseline, so a red CI diff means exactly one of the two is
   missing.
3. Spec-level changes move as one unit: `SPEC.md` +
   `schema/kolam-1.0.schema.json` + `src/core/` + `formal/z3/` + affected
   `examples/` + `docs/` (and README table if it changes "traditionally
   correct" claims). Never update the schema or validator alone.
4. Docs site (`site/`) is generated by `npm run docs` and gitignored; GitHub
   Pages deploys it from CI (`.github/workflows/deploy.yml`). Don't hand-edit
   `site/`, `dist/`, or `formal/z3/data/` — all generated.
5. Commit only what the task asks; keep generated and source changes
   separable in review (rule 2's same-commit requirement is the one pairing
   exception).

## Conventions

- ESM (`"type": "module"`, NodeNext): relative imports inside `src/` end in
  `.js` (e.g. `import { DotGrid } from './grid.js';`).
- Style: 2-space indent, single quotes, semicolons, trailing commas where
  legal. Keep the existing pattern of a doc-comment header on each module
  explaining its role in the model (see `src/core/gates.ts` for tone).
- Tests: `node:test` + `node:assert/strict` run via `tsx`, one file per
  concern in `test/` (`sanity` ground truths, `exhaustive` sweeps,
  `generator`, `prompt`). New behavior needs a test in the
  matching file; new model ground truths go in `sanity.test.ts` with the
  hand-verified reasoning in the header comment.
- Numerics: geometry uses exact dyadic rationals on the unit lattice; prefer
  integer/half-integer arithmetic over floats in `src/core` and `src/render`.
- Terminology: dots are *pulli*, gates are open/closed (never "pixels" or
  "cells" for gates), loops/strokes as in SPEC §terminology; prastāra index =
  the bijective gates↔index encoding (`encodeIndex`/`decodeIndex`).

## Pitfalls

- Don't "simplify" reflection/crossing logic — open gate = straight through,
  closed gate = reflect (horizontal wall → negate dx, vertical wall → negate
  dy); boundary gates (one flanking dot) are always closed and may not carry
  a bit.
- Loop counts are physical curves (orbits pair up per direction); report
  `analysis.isOneStroke` / loop counts honestly — multi-loop kolams are
  traditional, never silently collapse or merge them.
- Grid dialects differ: rectangular, diamond (`diamond:n`), row-count arrays,
  and Tamil `7-1` shorthand in the prompt parser (`src/prompt/parser.ts`) —
  they must agree on gate/node coordinates via `src/core/grid.ts`.
- Exhaustive tests sweep up to 2¹⁶ configs; keep additions there bounded and
  fast (the whole Tier-A run is CI's hot path).
